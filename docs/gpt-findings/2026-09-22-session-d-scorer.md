# Session D scorer written before collection

**Job:** `docs/agents/GPT-PROMPT-NEXT.md` Job 3. I wrote
`analysis/score_session_d.py` for the four RTX 3070 Ti Session D suites, with
synthetic tests in `analysis/test_score_session_d.py`. I exposed the existing
argmax as `analysis/analyze_sweep.py:efficiencyPeak` and made `describe` use it
too. No Session D measurements were supplied or generated. The script does not
change GPU state.

## Scoring rule

- The registered inputs are taken from
  `data/frequency-sweeps/rtx3070ti-20260825/SESSION-D-RUNSHEET.md`, especially
  Edit 1, Edit 2, and "What each outcome means". The numeric values and run
  order live in `SessionDRegistration` so a precollection edit is a visible
  one-place change. The 25 MHz tolerance for "~1500" is an **analysis choice**, not
  a number in the runsheet; it is under one quarter of the 105 MHz grid step.
- `analysis/analyze_sweep.py:loadSweep` supplies the existing sweep filter,
  achieved clock, and throughput/power efficiency. Both `describe` and this
  scorer call `efficiencyPeak` to select the maximum-efficiency row. The scorer
  then takes the median achieved optimum across 12 workloads. Individual picks are
  reported but do not determine the verdict. The previously observed 9/12
  agreement is from one stock repeat pair, so it is a caution, not a new
  estimate of repeatability.
- The six Edit 2 high targets are one operating bin per workload. Its efficiency
  is the median of their six `loadSweep` efficiencies; the scorer does not give
  six noisy observations six chances to win an argmax. It reports that bin's
  achieved clock. The runsheet requires one bin but does not prescribe the
  within-bin summary; the median is an explicit preregistration choice here.
- Voltage extracts are required for every sweep. The script reports the highest
  **sampled** floor clock and lowest sampled above-floor clock per run, and
  checks the expected stock, Edit 1, and Edit 2 regions in every workload.
  These extracts are evidence that the edit took under load, but cannot prove
  every point of the saved Afterburner curve; the raw profile snapshots remain
  necessary for that stronger claim.
- Run 4 must reproduce run 1's median optimum and each workload's median
  absolute matched-target throughput change must be at most 1.5%. That
  operationalizes the runsheet's approximate drift cutoff conservatively.
  The script withholds effect verdicts for a failed bracket, a missing or
  inconsistent voltage extract, an unverified curve region, or a stock median
  that is not the registered 1485 MHz baseline.
- A valid 4a pass requires a 1170 or 1275 MHz median. A valid 4b pass allows
  1485 through 1500 MHz achieved. Joint outcomes distinguish both passing,
  Edit 1 moving with a moved control, no downward Edit 1 movement, an
  unpredicted downward bin, both predictions failing, and drift or invalid
  manipulation. These are verdicts on **one second chip**, not generalization.

## Provenance issue to resolve before collection

`docs/REGISTERED-PREDICTIONS.md` §4a still says to **extend** the floor upward
using points at or below 0.819 V, and §4b says an above-floor change of at least
300 MHz. The later Session D runsheet instead instructs **shortening** the
floor downward at or below 0.825 V and describes a 263 MHz control dose. The
runsheet records its boundary correction as 2026-09-20 and says this happened
before collection. This scorer follows the Job 3 designated runsheet. The
relationship between the original registration and the later amendment must
be stated when reporting the hardware result; it must not be described as if
the original §4 wording predicted the eventual direction and dose. Neither
source was edited here.

## Verification and limits

The synthetic suite exercises a pass, unchanged Edit 1 failure, moved control,
both failures, unpredicted downward movement, drift, one missed curve edit,
missing voltage, floor extents, and the six-row binning selection rule.
Synthetic tests establish the script's decisions for those fixtures; no real
Session D data or HWiNFO log has been scored. No hardware run was performed.

All numeric hardware predictions above are **quoted from the runsheet**, not
recomputed. The 12-workload and 13-target sizes are checked against the
runsheet; the test outcomes and gate counts are generated by the code. The
precollection script has not been committed in this session, so its analysis
registration will become tamper-evident only when committed before data
collection.

## Review by Claude, 2026-09-22 — accepted after one correction to the scoring rule

**Verified as right:**
- `analyze_sweep.py`: the change is a **pure refactor**. It moves the same `max(...)` into
  `efficiencyPeak()`, with identical behaviour.
- The JSON fields the scorer requires exist in real 3070 Ti sweep files: `session_label`,
  `gpu_name`, `driver_version` and the three power-limit fields, reading 290 / 290 / 320 W.
- `Collect.ps1` labels runs `$Label-$workload`, which is exactly the name pattern the scorer matches.
- The runs are refused, not scored, when a voltage extract is missing, a workload's edit was not
  applied, the driver changes mid-session, or the BIOS position is wrong.
- The Edit 2 median-of-six bin is the right answer to the runsheet's max-of-six concern.

**⛔ Corrected: the optimum was scored on the ACHIEVED clock and tested for EXACT equality** with
the registered grid numbers: baseline `== 1485`, run 4 `== run 1`, and 4a `in (1170, 1275)`. Every
fixture set achieved equal to target, so no test could see it. With a **0.6 MHz** offset, a
passing fixture came back **NOT_SCOREABLE**. The 3070 Ti does land exactly on target when
unclipped (checked on the 09-04 suite), so the bug might never have fired there. But a verdict
must not depend on that. **Now:** each workload's optimum is its **target grid point**, the unit
the predictions are written in. Edit 2's clipped bin counts as 1500, its registered achieved
value. Achieved clocks are still reported, but never scored.

**⛔ Corrected: the 4a pass rule was set membership.** With twelve workloads, six at 1170 and six at
1275 give a median of **1222.5**. That is inside the registered range, and it was scored
`FAIL_OTHER_DOWNWARD_BIN`. **Now:** 1170 ≤ median ≤ 1275.

Two tests were added. **Each was confirmed to FAIL against the original logic**, so neither is
vacuous.

**Kept as GPT designed it, and worth knowing before the session:** the run is **not scoreable**
unless stock run 1's median is exactly 1485. A stock median that splits between two grid points,
say 1432.5, blocks every verdict. That is strict, and it is defensible because 1485 is the
registered baseline. But it means a stock suite that fails to reproduce 09-04 costs the whole
session.

**GPT's provenance finding is CONFIRMED and now recorded** in `REGISTERED-PREDICTIONS.md`, as an
amendment block under §4b. The design reversed from "extend upward" to "shorten downward" on
2026-09-13, two days after registration and before any collection, and the ledger never said so.
The control's dose is 263 MHz, against the ≥300 MHz registered.
